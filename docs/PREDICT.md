# PREDICT snapshot (desktop)

Open **PREDICT satellite tracker** from the main menu. Run a compatible PREDICT server separately, then enter its numeric IP address and UDP port. Choose **Load satellites** and select a tracked satellite, or type its exact name manually; choose **Read snapshot**. In single-satellite mode the list includes only the satellite PREDICT is tracking. The window displays the returned position, next AOS/LOS event, Doppler normalized to 100 MHz, receipt time and the TLE epoch. For repeated readings, enable **Refresh automatically**: the next request starts 2.5 seconds after a successful response. An error or closed window stops the cycle and hides the previous sample. Use **Predict next pass** for the next pass from the present time and **Following pass** to request the one after the displayed LOS. The window shows AOS, LOS and maximum sampled elevation alongside the TLE epoch. Predictions can be cancelled locally; PREDICT may continue processing an already received request. The pass reader rejects out-of-order data, missing endpoints, gaps over 180 seconds and streams exceeding its time or size bounds, so some valid slowly sampled passes may be rejected. UDP cannot guarantee delivery; a successful response cannot prove that no packets were lost. No equipment is controlled.

For both a snapshot and pass prediction, DecoDXLog requires the two TLE lines to use the 69-column format, have matching catalogue numbers and valid checksums, and contain a valid epoch. A malformed or non-standard response is rejected. The check does not authenticate the source, prove that the provided name corresponds to the catalogue number, or validate the full orbit.

PREDICT controls its own orbital data and station coordinates. The window warns when the TLE epoch is in the future or more than 14 days old; that threshold is a caution, not a guarantee that newer data are suitable. Update the tracker data and verify its station configuration. The snapshot brackets position and Doppler reads with matching TLE reads and matching tracking-mode checks. The receipt time is when the position response arrived; PREDICT may still return its last calculated position. These checks cannot prove that every sample is current, even with refresh enabled. The sample is hidden when a new request fails. A timeout or invalid response is shown as an error.

The default **Independent frequencies / FM** model keeps the two entered nominal frequencies independent, as before. For a linear transponder the operator may choose inverting or non-inverting, enter nominal uplink and downlink centre frequencies, a signed uplink offset in kHz and the permitted half bandwidth. The model applies an ideal 1:1 offset (opposite sign on the downlink when inverting), then previews Doppler as usual. An offset outside the entered bandwidth is rejected. These values are manual, not a satellite catalogue: check current frequencies, applicable band plans, transponder direction and operating mode independently. This is a fixed calculation, not automatic tracking or radio tuning. See the [AMSAT linear satellite descriptions](https://www.amsat.org/live-linear-satellites/).

DecoDXLog's clients send only PREDICT read/prediction commands. PREDICT 2.2.x invokes a local helper through a shell for predictions, so pass requests restrict satellite names to a safe ASCII allowlist; server configuration and executable paths must also be trusted. It does not command CAT, PTT or a rotor. Enter nominal uplink TX and downlink RX frequencies to preview PREDICT’s normalized Doppler correction or explicitly prepare a QSO draft. Preparation requires a reading no more than 10 seconds old and a TLE epoch no more than 14 days old or in the future; these limits cannot guarantee a correct orbit or operating frequency. The draft contains fixed snapshot frequencies and does not track subsequent changes. Review it and save explicitly. Reopening a draft does not overwrite an already open satellite draft. It currently requires a numeric address, has no server discovery, and has no TLS or authentication; use it only on a network where the server and path are trusted. The software was checked against a local PREDICT 2.2.5 instance using old test elements; current predictions, radio hardware and other platforms have not been verified. See `docs/evolution/PROGRESS.md` for evidence.

When the satellite, propagation and TX/RX values are unchanged from a tracker-generated draft at initial save, the QSO stores the snapshot receipt time as `APP_DECOLOG_TRACKER_SNAPSHOT_UTC`. The time identifies the source snapshot only; it does not confirm the radio's actual frequencies, a valid orbit or a contact. If the draft values are changed before saving, this time is not stored. A local QSO edit or bulk edit changing satellite, propagation or either frequency removes this timestamp from the current QSO while preserving the previous record in QSO history. Other update paths may retain source-provided metadata; compare QSO history before drawing conclusions about current values.

**Plan passes** obtains up to ten sequential passes. The minimum sampled elevation filter hides passes whose reported sampled maximum is below the chosen threshold; it filters the already requested set and does not search further to replace hidden passes. A selected planned pass is cleared if the threshold hides it. Sampled maxima depend on the tracker output and can miss a true peak; this is a planning aid, not a visibility or contact guarantee.

The optional planning start accepts an explicit UTC timestamp in `YYYY-MM-DDTHH:MM:SSZ` form; leave it blank to start from the current time. It applies to **Predict next pass** and **Plan passes**. **Following pass** starts after the selected LOS. Changing the planning start hides the previous plan and selection. Dates beyond the tracker's accepted range or invalid calendar dates are rejected before sending a prediction request. A future prediction still depends on the supplied TLE and may be inaccurate.
