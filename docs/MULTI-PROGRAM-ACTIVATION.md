# Additional activation references

An activation keeps its existing primary kind and reference. The desktop activation dialog can also hold additional POTA, SOTA, WWFF and IOTA operator references. POTA accepts a comma-delimited list; SOTA, WWFF and IOTA accept one additional reference each. If the additional programme is also the primary kind, both reference values must agree. These checks validate syntax only: the app does not confirm a reference exists, that the operator was in its activation area or that a contact meets a programme's rules. The original primary-reference validation remains unchanged.

For new QSO logged while the session is active, the app fills the corresponding operator ADIF fields (`MY_POTA_REF`, `MY_SOTA_REF`, `MY_WWFF_REF`, `MY_IOTA`) without replacing values already present in that QSO. Contacted-station references such as `POTA_REF`, `SOTA_REF` and `WWFF_REF` remain separate. The legacy `MY_SIG`/`MY_SIG_INFO` fields continue to represent the primary kind where the existing code uses them; they cannot represent several programmes at once. Changing the session affects later QSO, not records already logged. Active-session settings survive a restart. New sessions have a durable identity and configuration change journal; detailed site/operator periods are not yet modelled.

The existing session QSO total is a local time-based count, not a programme-specific eligible-contact count. The existing generic ADIF export is **not partitioned** by programme, park, operator, location or UTC day and is not a verified submission file. For example, the [POTA logging rules](https://docs.pota.app/docs/rules.html) specify one park per log in a single location; the [POTA logging guide](https://docs.pota.app/docs/activator_reference/logging_made_easy.html) describes preparing separate logs for multiple parks. [WWFF's submission guidance](https://wwff.co/rules-faq/confirming-and-sending-log/) describes its use of `MY_SIG_INFO`. Do not submit the generic combined export as if it already implemented these programme-specific requirements. [ADIF 3.1.8](https://www.adif.org/318/ADIF_318.htm) defines the separate operator reference fields and POTA reference lists.

Per-programme partitioning and previews, official validation, local catalogue/version updates, site/operator periods, reliable per-programme counts, real importer acceptance and hardware/RF tests remain open. The added SOTA syntax check is deliberately structural and does not validate a summit catalogue. A reference already present on an individual QSO is preserved even if it conflicts with the session; review such records manually.

New sessions persist a UUID and start/update/stop snapshots transactionally with the active setting. QSO receiving the activation fields carry `APP_DECOLOG_ACTIVATION_UUID` unless already present; imported or edited values are reported metadata, not proof of membership. Legacy active sessions have no inferred UUID, and network-received QSO may bypass activation application. The existing counts and generic export are still time-based and do not use this identifier. No closed-session browser or programme partition export is provided yet.

The active session offers a read-only grouping of QSO that report its UUID by programme, operator reference, UTC date, operator and grid. It runs on a read-only background connection and displays groups in pages of 100. It counts missing date/reference separately and is not an eligibility calculation, an export or proof of session membership. Cancellation discards the result.

From a current grouping preview, POTA and WWFF groups can be exported separately by programme, operator reference, UTC date, operator and grid. The file copy sets the chosen operator reference and `MY_SIG`/`MY_SIG_INFO`; the personal log and counterpart reference fields are unchanged. This export does not yet validate eligibility, required fields, location, duplicates or the programme catalogue; check the resulting file and applicable rules before submission. SOTA/IOTA-specific export is still outstanding. The preview fingerprint detects membership and app-managed QSO revision changes before a consistent export snapshot, but not arbitrary database changes that bypass revisions or changes after the snapshot.
