# ContestNet QSO convergence foundations

The existing ContestNet QSO path remains the legacy UDP path. The schema-28/29 change journal and `ContestNetInventory` are local foundations and do not currently transmit or apply QSO revisions.

An inventory opens an existing schema-29-or-newer file read-only and starts one SQLite read transaction. Schema 29 is required because schema 28 does not journal QSL-only changes. Its log identity and journal watermark are obtained from that snapshot; pages enumerate QSO ID, UUID, revision, soft-deleted state, a content fingerprint and a UTF-8 ADIF record in ID order, including pre-migration records and tombstones. Pages are limited to 500 rows and a configurable returned-payload budget (default 1 MiB, maximum 16 MiB). If a single next record exceeds that budget, the call reports an error without advancing the cursor; the caller can retry with a larger permitted budget. The limit covers returned ADIF bytes, not all temporary SQLite and string allocations. Each payload is parsed again using this application's ADIF parser and must reproduce the fingerprint, or the page fails without partial results. Closing or destroying the inventory releases the transaction. The object and its SQLite connection must remain on their creating thread.

A future reconciliation can compare that inventory, then inspect journal entries after its watermark. The fingerprint is SHA-256 of a version-tagged Qt 6.0 `QDataStream` in big-endian format: a field count followed by ADIF field names sorted lexically and their exact values. It covers fields returned by `recordChecked`, including ADIF-visible QSL state; it does not include QSO UUID, revision, attachments, station-profile records, local QSL remote IDs or other non-ADIF metadata. It is a candidate comparison aid, not proof of semantic equivalence: different formatting can produce different fingerprints and a cryptographic collision is theoretically possible. A failed QSO or QSL query or malformed/non-string ADIF extra data aborts the page rather than hashing missing data. The current implementation performs separate QSO and QSL queries per row; it requires realistic large-log performance testing before use in an interactive workflow.

Journal entries are only local metadata; there is no peer acknowledgement, ordering contract, conflict policy, checkpoint or implemented replay. The inventory ADIF payload may contain private QSO notes and QSL fields, and is not sent over the network by this increment. A record exceeding the maximum budget requires a separate future large-record transport; no fragmentation is implemented. Round-trip validation uses this application's parser and does not establish interoperability with another ADIF implementation. Schema 29 journals QSL inserts, removals and changes to ADIF-relevant status fields, including changes which do not increment the QSO revision; changes only to local remote ID or error text do not create entries. A QSL move between QSO records both identities. Entries may be conservative duplicates and do not contain snapshots. Arbitrary raw SQL changes to QSO content without a revision/identity/deletion change, physical QSO deletion and non-ADIF data are still not covered. UUID adoption and Cloud revision updates can generate entries, and a QSO revision is not necessarily monotonic across Cloud operations. The sequence and log identity cannot prove continuity across a restored or copied database without additional binding and validation.

The inventory checks the file identity captured on open before and after each page, and stops if the path is replaced. Capturing the token from the path after opening SQLite is not atomic with the SQLite open; in-place changes, file-ID reuse and network-filesystem semantics are not covered. Keep read transactions brief: in WAL mode a long snapshot can retain WAL pages, while rollback-journal mode can block writers. The current API has no asynchronous UI integration, automatic deadline or resumable snapshot after process restart.
