# ContestNet QSO convergence foundations

The existing automatic ContestNet QSO path remains the legacy UDP path. A separate manual experimental transfer can send one selected snapshot QSO as fragments; it does not automatically apply the received record. The schema-28/29 change journal is local and does not automatically transmit or apply QSO revisions.

An inventory opens an existing schema-29-or-newer file read-only and starts one SQLite read transaction. Schema 29 is required because schema 28 does not journal QSL-only changes. Its log identity and journal watermark are obtained from that snapshot; pages enumerate QSO ID, UUID, revision, soft-deleted state, a content fingerprint and a UTF-8 ADIF record in ID order, including pre-migration records and tombstones. Pages are limited to 500 rows and a configurable returned-payload budget (default 1 MiB, maximum 16 MiB). If a single next record exceeds that budget, the call reports an error without advancing the cursor; the caller can retry with a larger permitted budget. The limit covers returned ADIF bytes, not all temporary SQLite and string allocations. Each payload is parsed again using this application's ADIF parser and must reproduce the fingerprint, or the page fails without partial results. Closing or destroying the inventory releases the transaction. The object and its SQLite connection must remain on their creating thread.

A future reconciliation can compare that inventory, then inspect journal entries after its watermark. The fingerprint is SHA-256 of a version-tagged Qt 6.0 `QDataStream` in big-endian format: a field count followed by ADIF field names sorted lexically and their exact values. It covers fields returned by `recordChecked`, including ADIF-visible QSL state; it does not include QSO UUID, revision, attachments, station-profile records, local QSL remote IDs or other non-ADIF metadata. It is a candidate comparison aid, not proof of semantic equivalence: different formatting can produce different fingerprints and a cryptographic collision is theoretically possible. A failed QSO or QSL query or malformed/non-string ADIF extra data aborts the page rather than hashing missing data. The current implementation performs separate QSO and QSL queries per row; it requires realistic large-log performance testing before use in an interactive workflow.

Journal entries are only local metadata; there is no peer acknowledgement, ordering contract, conflict policy, checkpoint or implemented replay. The inventory ADIF payload may contain private QSO notes and QSL fields; the separate manual UDP experiment can send it in clear text or using the optional shared-key mode. Inventory supports up to 16 MiB per record, while the experimental fragmented transfer has a 4 MiB maximum. Round-trip validation uses this application's parser and does not establish interoperability with another ADIF implementation. Schema 29 journals QSL inserts, removals and changes to ADIF-relevant status fields, including changes which do not increment the QSO revision; changes only to local remote ID or error text do not create entries. A QSL move between QSO records both identities. Entries may be conservative duplicates and do not contain snapshots. Arbitrary raw SQL changes to QSO content without a revision/identity/deletion change, physical QSO deletion and non-ADIF data are still not covered. UUID adoption and Cloud revision updates can generate entries, and a QSO revision is not necessarily monotonic across Cloud operations. The sequence and log identity cannot prove continuity across a restored or copied database without additional binding and validation.

The inventory checks the file identity captured on open before and after each page, and stops if the path is replaced. Capturing the token from the path after opening SQLite is not atomic with the SQLite open; in-place changes, file-ID reuse and network-filesystem semantics are not covered. Keep read transactions brief: in WAL mode a long snapshot can retain WAL pages, while rollback-journal mode can block writers. The current API has no asynchronous UI integration, automatic deadline or resumable snapshot after process restart.

`ContestNetReconcile` compares two local, independently pinned inventories in SQLite binary UUID order with bounded internal pages. It reports local-only, remote-only, matching fingerprint, revision difference with matching fingerprint, content conflict, or deletion-state conflict. It does not infer that a higher revision wins, automatically merge QSLs, match different UUIDs by callsign/time, change either database, or send data to a peer. A matching fingerprint covers only the documented ADIF projection and does not imply that attachments or other local metadata match. The two snapshots are opened sequentially and have separate watermarks; changes after either snapshot require a future catch-up protocol. Callers must discard the entire comparison if a later page fails, including any earlier pages, and close the snapshots promptly. A configurable per-source payload budget is capped at 16 MiB; an oversized first record aborts comparison rather than skipping it. File identity checks also cover rows buffered between pages, subject to the filesystem limitations above.

The station-network panel offers a read-only offline comparison against a user-selected local log file. It runs on a worker, counts all classifications, and shows the first 200 differences with QSO summaries. Where both records exist and their ADIF fingerprints differ, it also lists up to 32 differing ADIF fields with values from each side and distinguishes missing fields; additional fields and names or values longer than 256 UTF-16 code units are marked as omitted or truncated. A truncation does not modify the stored value. These previews may contain private QSO notes and QSL data and remain local. They do not include attachments or fields outside the ADIF projection. A separate per-QSO review can apply a chosen change after confirmation. Cancellation is checked between pages. The UI checks the open log and a separate read-only SQLite connection for commits to the selected log, and marks the result stale when either changes or a file is replaced. Polling is periodic, so a result can be briefly stale before the next check; non-SQLite in-place file manipulation and filesystem races are not covered. There is no merge, remote peer protocol or resumable comparison.

See [PROGRESS.md](PROGRESS.md) for the tests actually run and remaining LAN, conflict and cross-platform work.

### Experimental single-record framing

`ContestNetQsoTransfer` defines a version-1 JSON fragment contract around a single inventory ADIF payload, using 512-byte raw chunks for the original mode or 256-byte chunks for protected mode, strict metadata and a 4 MiB maximum. A receiver is bound to an expected sender identifier and transfer ID, accepts out-of-order and duplicate fragments, and only releases a record after checking both payload SHA-256 and the existing ADIF fingerprint. These checks detect accidental corruption; sender IDs and hashes are not authentication. The manual experimental controller can hold one outgoing and one incoming transfer, with a five-minute expiry and explicit operator initiation; it does not persist transfers or automatically apply received QSO. Without a key it broadcasts in clear text; the optional shared-key mode protects this transfer only. Records above 4 MiB cannot be transferred.

An explicitly armed receiver requests the first fragment or up to 32 missing indices every two seconds. Missing-index requests are bound to the transfer ID and payload hash; the sender validates them and limits responses to one request per second from the configured logical peer. An integrity failure stops retries and requires rearming. In clear mode requests are unauthenticated; protected-mode requests prove possession of a shared key, not an individual identity. Retry state is not durable.

An experimental `applyMissing` operation can transactionally insert a fully reassembled non-deleted record into an explicitly identified local file-backed log. It checks the persisted ADIF fingerprint, refuses duplicate or divergent existing records, and does not overwrite existing QSO. Both offline comparison and the experimental network receiver can invoke it only after explicit per-QSO review and confirmation. ADIF-visible fields alone do not include attachments, local service metadata or station-profile assignments.

A separate experimental review token can guard a caller-selected edit or soft deletion of an existing local QSO. It compares the local revision, deleted state and ADIF fingerprint and the received payload again inside the write transaction; local revisions continue independently. This is a primitive for a future operator review, not an automatic conflict policy. The review also guards QSO columns, service metadata, enrichment rows, attachment metadata/link state and attachment binary data, read in bounded slices. Both offline comparison and the experimental network receiver use the guard after confirmation.

A pinned inventory can also fetch an individual UUID without advancing its page cursor. The lookup returns the same snapshot content and uses the same payload and file-identity guards as pagination; it does not itself authorize or apply a change.

The offline comparison UI can inspect all ADIF fields of a displayed difference using direct UUID lookup in fresh pinned snapshots, guarded against observed log changes. The inspection is read-only; after a separate confirmation the operator can import a missing, non-deleted QSO into the open log. Long values have a paged viewer; attachments/local-only metadata are not displayed or copied.

For an existing non-deleted local QSO, the offline inspection can also explicitly apply the selected ADIF fields or a selected deletion after a separate confirmation and a transactional local-state recheck. It is not automatic merging. Long fields must be traversed page by page before import/apply is enabled; attachments and station profiles are retained locally and are not copied. Normal configured QSL/service edit or deletion workflows may run.

### Optional shared-key protection

The manual experiment may use a random 32-byte key exchanged outside ContestNet. XChaCha20-Poly1305 protects the QSO fragment and retry-message contents, with the normalized group, logical sender and recipient bound as associated data. Nonces are generated randomly for each packet; accepted nonces are remembered in memory up to 32,768 entries, with no persistent replay protection across reset or restart. Use a new random key and transfer ID for each session. When a key is active, unprotected experimental packets are ignored; protected packets are ignored when no key is active. This does not authenticate individuals sharing a key. Group, sender/recipient IDs, station name, sequence/session metadata, timing and packet lengths remain visible; outer sequence, session and name are not authenticated. Other ContestNet and legacy QSO traffic remains unchanged and unencrypted. The UI does not save the key, but Qt and operating-system memory copies are not guaranteed erased.

Protected chunks use 256 raw bytes to reduce double-base64 overhead; original 512-byte frames remain unchanged. Before transmission the controller rejects a protected UDP payload above 1,472 bytes based on the serialized envelope, suitable for a typical 1,500-byte IPv4 link but not a guarantee for VPNs or smaller path MTUs. Very long identifiers may therefore be rejected. The implementation uses the project's vendored Monocypher API; see [Monocypher AEAD documentation](https://monocypher.org/manual/aead). This experimental protocol has not had an independent security audit or multi-host interoperability validation.

A completed experimental network transfer can be compared with the current local QSO, including paged long-field review, then explicitly imported, updated or soft-deleted using the same guarded operations as offline review. The received snapshot can be stale relative to the sender; shared-key mode verifies key possession rather than individual identity, and clear mode has no authentication. Rearming, closing or expiring the transfer invalidates its pending review. This is a one-record, operator-directed action, not automatic journal convergence.
