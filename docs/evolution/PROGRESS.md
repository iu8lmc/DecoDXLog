## 2026-11-22 — G05 guarded recovery backend

Schema 13 adds an import-time fingerprint of the complete QSO row, per-service QSL state, attachment metadata and enrichments. It is calculated and recorded within the QSO import savepoint. The durable `undoLatestImport` operation opens a transaction per journalled QSO, checks its local ID, persistent UUID, revision and fingerprint, and soft-deletes only unchanged records. Already-deleted, missing/replaced, changed and failed records are counted separately; a later retry does not repeat completed deletions. Schema-12 journal entries have no baseline and are conservatively skipped for review. A profile change or service update that modifies the stored row can produce a conservative skip. After removing the trigger, retry returned the ordinary duplicate response and the QSO count stayed at one. The same app fixture covered the existing keyed replay after restart and context conflicts. The QSO write and response journal remain non-atomic; process death or a lost HTTP reply can leave the client without this warning. Per-record results describe local processing, not completion of external QSL services. The duplicate check is not a general exactly-once guarantee, and an automatic client retry without reconciliation can still be unsafe. This change does not establish cross-process serialization or test other platforms or real services; remaining G11 and desktop roadmap requirements remain open.

## 2026-11-23 — G01 QSO insert rollback within an outer transaction

`LogDatabase::insertQso` now uses a SQLite savepoint around the QSO and its QSL status writes. This works both on its own and within a caller's existing transaction: a QSL write failure rolls back this insert rather than leaving a partial QSO for the outer transaction to commit. Savepoint creation and release are checked, failed results no longer expose a newly allocated QSO ID after a QSL or release failure, and the error is retained. The surrounding transaction remains the caller's responsibility.

A/B: a database fixture began an outer transaction and injected a failing QSL insert trigger. Before the change, `insertQso` returned an error but left one QSO visible in that transaction. Afterwards the count remained zero; after removing the trigger, the same outer transaction inserted the QSO with its LoTW status and committed successfully. On macOS arm64/Qt 6.11.2 the app and relevant targets built, CTest database, contestnet, migration and netcontroller passed 4/4, and the actual app's offscreen local API fixture including journal-failure injection passed.

This does not make the API's QSO and idempotency-response writes atomic or defer external side effects until the caller's outer commit. Duplicate lookup still precedes the savepoint and is not a cross-process uniqueness guarantee. Savepoint release failure, power loss, physical hardware, external services and Windows/Linux were not independently fault-injected or verified in this increment. Remaining G01, G11 and desktop roadmap requirements remain open.

## 2026-11-23 — G01 preserve QSL state on read failure

`writeQsl` now stops if reading existing service state fails, including an error while iterating rows, before deleting any existing QSL entries. The edit savepoint then rolls back the QSO and history changes. This preserves non-ADIF service information such as remote IDs when the prerequisite read fails.

A/B: with the macOS Qt SQLite driver verified to link the system SQLite library, an opt-in database fixture used SQLite's native authorizer to deny reading only `qsl_status.last_error`. This injects an authorization error, not disk corruption, mid-stream I/O failure or power loss. Snapshot and other database read paths need separate error audits, and actual remote-service behavior, Windows and Linux remain unverified. Remaining desktop roadmap requirements remain open.

## 2026-11-23 — G01 reject incomplete QSO history snapshots

Before editing or soft-deleting a QSO, the history snapshot now uses the existing checked record reader and the operation refuses to continue if the record, QSL states or metadata cannot be read. This avoids committing a history entry that silently omits inaccessible QSL fields. The existing operation savepoints roll back and expose an error. The checked reader also rejects malformed or non-string ADIF-extra JSON, so affected legacy records must be repaired before they can be edited or deleted through these paths.

## 2026-11-23 — G11 refuse keyed API requests on journal lookup failure

The local API now distinguishes a missing idempotency entry from an error during expiration cleanup or lookup. If the journal is unavailable, it returns HTTP 503 before parsing or processing a keyed QSO request. Successful and unkeyed operations are unchanged; the API guide distinguishes this case from a failure to save the result after processing.

A/B: an actual macOS arm64/Qt 6.11.2 app running offscreen used a temporary test log. A second SQLite connection temporarily renamed the idempotency table before a keyed request. The test simulates an unavailable table rather than disk failure or power loss; Windows/Linux, real services and the remaining G11 and desktop roadmap requirements remain open.

## 2026-11-23 — G04 discard externally stale goal-alert results

Goal-only campaign alerts now capture the open log generation and SQLite `data_version` before starting the worker and recheck them, along with the open file identity, before emitting. If another connection commits, the log is reopened/replaced, or the stamp cannot be read, the pending result is discarded. Existing in-process log-version, campaign revision, profile, spot-filter and freshness checks remain. A later matching spot can start a fresh check.

A/B: a focused two-connection fixture demonstrated that the previous generation-only check remained satisfied after the second connection inserted a QSO, while the new check rejected the stale stamp and accepted a refreshed one; it also rejected a closed log. Any external database commit can discard an otherwise valid pending alert, and the result is not automatically retried without a new spot. A commit after the final check remains possible; there is no lock spanning the UI alert. The test did not force an actual two-process app race, use a real cluster or RF, or verify Windows/Linux. Remaining G04 and desktop roadmap requirements remain open.
