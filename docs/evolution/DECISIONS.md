# Decisions

- Preserve existing award and import models; add evidence and contracts incrementally. A confirmed QSO is not automatically an official award credit.
- The web contest calculation remains the existing generic model while explicitly labelled as an estimate. Shared official scoring remains open; no scoring semantics changed.
- Marathon edition matching uses UTC for all timestamp representations; database loading already converts to UTC. This prevents equivalent instants receiving different edition decisions.
- Synthetic fixtures and real exports, simulated peers and real hardware, local build and packaged releases must be recorded separately. No mobile development.
- Keep the legacy Marathon `selected` entity array and add a separate `zoneCandidates` array so existing consumers retain their entity-selection contract. Candidates are explicitly unverified; a numeric CQ zone range is not proof of a valid program entry or location.
- Require an explicit station profile for Marathon preview in the desktop UI, while preserving the selector's existing all-profiles API for other callers. This avoids silently combining profiles, but is not evidence that a profile contains one operating location. Use atomic replacement for the internal JSON export.
- Import batches must own their transaction; refusal is explicit if one is already active. Each QSO insertion uses a savepoint so a failed QSL subwrite cannot commit an unreported QSO. Committed prior batches remain available after a later failure; import progress is emitted only for committed batches. Measure savepoint overhead on representative logs.
- Schema 12 journals successfully inserted `source=import` QSO in the same transaction as their creation, retaining persistent UUID and revision alongside the local ID. The journal does not retroactively describe previous imports. The migration is additive and transactional; restoring an earlier version requires a verified pre-upgrade backup because downgrade is untested. The journal is a prerequisite, not proof that undo is safe or available.
- Schema 13 retains an import-time fingerprint covering the QSO row, QSL service state, attachment metadata and enrichments. Undo checks local ID, UUID, revision and fingerprint inside a transaction before soft deletion; incomplete legacy baselines fail closed. This intentionally favours review over deleting a changed QSO. Do not run this synchronous core loop on the UI thread for large imports; optimise and measure fingerprint cost.
- Run import undo on the import worker pool with its own SQLite connection. Cancellation is cooperative between QSO transactions; completed soft deletions are retained and retries remain idempotent. Require explicit UI confirmation; a generic warning is not a replacement for the still-pending per-QSO review.
- Reuse prepared fingerprint and journal queries within a single owning `LogDatabase` operation, preserving the existing schema-13 fingerprint bytes. Statements are not shared across worker threads. Prepared-query reuse reduces but does not eliminate the measured overhead; the representation must be explicitly versioned or preserved when QSO columns change.
- Report per-record undo exclusions after processing, with a bounded first 200 issues and explicit omitted count; do not show the callsign of a different QSO occupying a stale ID. This is not yet a pre-operation or exhaustive review. Recheck identity and baseline during each mutation even when a future preview is added.
- Preview undo asynchronously and bind confirmation to both the current log path and the reviewed import batch's ID and UUID. Treat per-record preview totals as advisory because the log can change; recheck identity and fingerprint in each deletion transaction. A legacy no-argument controller invocation retains its previous latest-batch semantics, while the desktop confirmation requires the reviewed identity.
- Bound undo/preview journal reads to keyset pages of 128 entries, with an initial cancellation point and an indexed `(batch_id,qso_id,qso_uuid)` order in schema 14. The initial count and maximum ID bound the scan but do not guarantee a stable membership snapshot under external writers; do not present them as one.
- Schema 15 uses transactional SQLite triggers to increment a batch journal revision on each insert/update/delete. The desktop preview token includes batch ID, UUID and revision; the worker rechecks membership inside each QSO transaction and at scan end. A mismatch stops safely but does not roll back earlier committed QSO deletions. Triggered membership stability does not imply a coherent snapshot of QSO data.
